# Serialize Wiki publication per Vault

All Folio-originated Wiki writes, including Agent results and future UI file edits, enter one durable FIFO publication queue per Vault. Only the head item may change the canonical Wiki; if it conflicts, it retains the head until the complete Wiki change is resolved, so later publications cannot pass it and observe a knowledge state that omitted earlier work.

This single-writer model replaces repeated per-commit replay and resolution-patch rebasing with one aggregate Task result applied to the canonical Wiki. Raw publication may continue because it does not write `wiki/**`; a later raw-only main commit changes the Git parent but not the Wiki conflict input. Direct external commits are not a supported publication path: Folio detects the low-frequency main change before publishing and reevaluates the head item against the latest canonical Wiki rather than designing normal queue concurrency around an uncontrolled writer.

One queue item freezes one complete publication intent. A Knowledge Task contributes the aggregate Wiki difference between its baseline and final result regardless of its internal Runs or intermediate saves, and conflict resolution updates that same item. A future UI edit creates its own item when the user explicitly submits it.

The queue reuses a redesigned `git_operations` table instead of introducing a separate publication table. One Wiki intent occupies one row ordered by its durable `sequence`; a nullable `task_id` associates Agent output while allowing future UI-originated items. The row advances through queueing and preparation to either conflict or the terminal `published` state, and its bounded local operation file retains crash-recovery data. Canonical merge plus its durable `published` receipt is business completion; later artifact or worktree cleanup is best-effort housekeeping and does not add a second completion state. Conflict resolution mutates this row and recovery artifact rather than creating a follow-up publication.

The previous `save-wiki` plus `synchronize` pair is removed. Intermediate Task-branch saves and Run attribution do not become queue items; the Knowledge Task freezes one aggregate result before admission. Raw Git operations may continue to use `git_operations`, but raw-only rows do not participate in the Wiki FIFO because they cannot modify `wiki/**`.

Implementation status for the first `raws → knowledge` delivery: Knowledge Tasks use one aggregate `synchronize` row and their publications respect the order of active Wiki synchronization rows. Existing manual Task review/save and direct Page editor writes still use their earlier paths. Converting those entry points to the common queue is remaining work before the Vault-wide single-writer claim above is fully true.

Entering conflict automatically starts a Conflict Agent for that queue head. If its proposed resolution fails deterministic Wiki validation, Folio returns the structured issues to the same Agent for repair rather than treating the invalid proposal as a publication outcome. Once the Agent resolves every conflict, validation passes, and the merge succeeds, that same intent becomes `published` immediately without another user-confirmation step. If the Agent execution fails or cannot resolve the conflict, the head remains blocked and the UI exposes its canonical-versus-intent diff. The user then picks the content to retain and completing all conflict decisions finalizes the merge for the same intent. Conflict handling neither discards the Task result nor creates a replacement queue row; later items remain blocked until the resolved head is canonically published.
