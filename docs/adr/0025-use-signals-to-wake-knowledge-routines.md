# Use Signals to wake Knowledge Routines

Canonical raw publication emits a lightweight Signal to wake Knowledge Routines, not a durable copy of the changed paths or a second processing ledger. Each Routine determines pending work from the Git diff between its own processing checkpoint and the canonical Vault history; startup reconciliation performs the same check so a missed notification cannot lose work. Duplicating publication diffs in Signals was rejected because Git already owns those changes and per-Routine checkpoints already own progress.

Signals are transient and coalescible. Folio stores no Signal rows, acknowledgements, delivery attempts, or consumer offsets: Vault startup, Routine enablement, and Task resolution reconcile each enabled Knowledge Routine's checkpoint with canonical Git, so a crash between raw publication and notification cannot lose work.

The `raws-changed` Signal is Vault-scoped and wakes every enabled Knowledge Event Routine. It carries no Integration ID, resource ID, path list, or commit cursor; each Routine independently decides whether work exists from its own checkpoint and the canonical raw history. A disabled Routine receives nothing and reconciles when enabled again.

While a Knowledge Routine has a Task in progress, further Signals coalesce instead of creating one Task per notification. Once that Task is resolved, the Routine checks its checkpoint against the latest canonical state and may create one follow-up Task for the remaining changes. This bounds Task creation during bursts without treating notification count as work count.

A Knowledge Task freezes `fromCommit` and `toCommit` from the Routine's checkpoint to a selected canonical commit when it is created. A null `fromCommit` denotes the first full snapshot; no separate mode discriminator is stored. Retries use the same endpoints even if new raws arrive, and newer commits remain outside that Task rather than silently changing its input after a failure.

The first implementation selects the current canonical head and gives one Task the complete pending raw diff. It does not split backlog by commit count, path count, or diff size; bounded batching is deferred until observed workloads justify its additional cursor-selection rules.

A Knowledge Routine without a checkpoint freezes the current canonical head and processes every raw file present there as a full snapshot; it does not manufacture a Git diff from the Vault's initial commit. Successful publication or a durable no-change result establishes that head as the Routine's first checkpoint.

The first version provides exactly one system-owned Raw knowledge intake Routine per Vault. Its persisted identity is the unique `{ type: "event", signal: "raws-changed" }` trigger rather than an extra system flag or Routine subtype. Folio creates it with the Vault and owns its trigger, knowledge-organization responsibility, and base instructions; it cannot be deleted or repurposed as an unrelated Routine. The user may enable or disable it, select its Agent and model, and supplement its goal without replacing the system contract. Entity extraction, relationship creation, source citation, and updates to existing Pages remain one coherent Agent responsibility instead of creating separate raw consumers with duplicate checkpoints, repeated reads, and competing Wiki publications.

This first delivery stops at the Knowledge asset layer: it curates evidence-backed Wiki entities, events, facts, decisions, relationships, and citations from raws. Action-system derivation and cognitive-trajectory analysis are explicitly deferred and introduce no triggers, checkpoints, or output schemas in this version.

The Routine's checkpoint is the `toCommit` of its latest completed Knowledge Task. A Task completes only after its Wiki publication intent reaches canonical main, or after it durably confirms that no Wiki change is required; if Git publication wins before that receipt, journal recovery completes the Task without rerunning it. Agent success, queue admission, conflict resolution, worktree alignment, and cleanup do not independently advance the projected checkpoint.

A Raw knowledge intake result does not wait for per-file human approval. The Agent may create and update non-trashed Wiki Pages using the existing ObjectTypes, but it may not delete Page files, set `trashed=true`, or modify `wiki/_types.json`; material without a suitable structured property remains in the Page body rather than mutating the Vault schema. A source recall is evidence for revising knowledge, not authorization to erase an asset. Folio validates that the complete result stays within the allowed Wiki Page paths, preserves raws and ObjectType definitions, satisfies Page invariants, and uses resolvable Folio Page links and pinned raw citations. When validation reports issues, Folio returns those structured issues to the same Agent so it can repair the complete result; an invalid result never enters the publication queue and is not partially published. Once valid, the aggregate result automatically becomes one Wiki publication intent. The checkpoint remains unchanged until that intent is published, while Git history provides later inspection and recovery.

A terminal Agent failure or user stop retains the same Task and frozen raw input, blocks later work for that Routine, and requires an explicit Retry. Validation issues are repair feedback inside the active Agent workflow rather than a terminal Task outcome. New Signals coalesce behind a terminally interrupted Task instead of creating later work. Process-loss and crash recovery remain automatic because they continue an unacknowledged execution rather than overturning a terminal outcome.
