# Curate knowledge against Vault goals

Raw knowledge intake previously turned broad source coverage into numerous Wiki Pages, including transient notices with little lasting value. Folio uses Vault-level Knowledge goals as the primary criteria for selecting and organizing material. These goals are distinct from action-system Goals and the Agent Routine's execution instruction.

A processed raw batch may legitimately produce no Wiki changes. Source coverage, entity mentions, and the availability of an ObjectType do not by themselves justify creating assets. Existing raws and their Git history retain the original evidence; the Wiki represents selected, curated knowledge.

Folio provides built-in Knowledge goals, each expressed in one natural-language sentence, rather than relying on a single generic organization instruction. Each Vault stores its goals in its existing `config.json`, with Content, Idea, and Question enabled by default in a new Vault. A Knowledge Task freezes its goals in the original Run prompt; retries reuse that snapshot and later goal edits apply to later Tasks. Content, Idea, and Question are ObjectTypes for the corresponding curation goals. Each ObjectType carries a Markdown `template` in `wiki/_types.json` to guide content writing after selection.

The Agent orchestrates Raw knowledge intake and calls System One through the `system_one` Agent tool. Git differences provide the new material, with the frozen current and prior content available when the difference needs context. The Agent selects the source context, makes repeated decision calls, and collects goal matches into one todo list for the current intake before processing that list. Each todo identifies a stable knowledge topic, its specific subject, matched goals, discussion context and one or more frozen message references; the Agent decides whether to create, update, merge, or leave knowledge unchanged, so a todo does not prescribe a new Page. System One supplies structured decisions; the Agent writes the knowledge content. Folio supplies the tool connection, frozen task input, goals, and workflow instructions, and retains responsibility for validation and publication.

System One uses the user's locally deployed service, which is fully compatible with the TypeSafe System One API (`POST /v1/systemone` with Bearer API key authentication). Global Agent Settings provide its base URL, API key, and model independently of the Agent's generation model. Non-secret settings and credentials follow the project's existing separate configuration and credential-storage pattern; the Agent receives a callable tool rather than credentials in its prompt.

The initial goal-matching rule admits a source/goal match for consolidation into topic-based todos when its match probability is at least 0.7, and skips pairs below that threshold. The Agent may read additional source context before judging again. A failed decision call is not a negative match. The threshold is an initial operating rule, not an empirically established accuracy guarantee.

The Agent persists the intake todo list and screening progress in a local file within its Task worktree. Recovery reads that file and the existing Wiki draft. This working record stays outside Wiki publication through an exact Git ignore rule; it is not a separate database work queue.

The tool is implemented for both Pi and Codex. It converts each goal into an independent native Noul question, validates the returned probability, and retries transport errors, HTTP 429, and HTTP 5xx at most twice within a 30-second timeout. `_intake-todo.md` records frozen commits and screening/todo progress; validation requires matching commits, `phase: completed`, and no pending checkboxes even when there are no Wiki changes. The implemented workflow and tool contract are described in [Knowledge intake design](../knowledge-intake-design.md).

Content quality is reviewed against complete discussions, including attribution, subject boundaries, corrections and resolutions. Missing information cannot establish that something is undecided. Templates preserve useful examples and source context while omitting unsupported sections. Message citations keep precise anchors; the preview highlights their matching records and supports expanding surrounding messages without treating proximity as a semantic thread. See [quality examples](../knowledge-quality-examples.md).
