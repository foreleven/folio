# Model Project history as related assets

The Knowledge asset layer represents important Decisions and general Events as independent Wiki Pages alongside Meetings. Each time-bearing asset links to the Projects and other assets it concerns; a Project timeline is a chronological projection over those links, not an Agent-maintained Markdown list copied into the Project Page.

Keeping Decisions distinct from actions preserves choices as durable, citable knowledge even when they later produce Tasks. Independent assets also let one Meeting, Decision, or Event relate to several Projects without copying its content into each Project, while retaining a generic Note only as a fallback for material without a stronger type.

Meeting, Decision, and Event share the same timeline-facing field: `occurredAt` is a timezone-aware instant. Decision has a lifecycle `status` with the default options Proposed (`not_started`), Accepted (`complete`), and Superseded (`complete`). Unadopted alternatives and review discussion remain in the Decision body or in Notes/Events rather than becoming rejected Decisions. A generic Event has no required `type` field because its meaning is carried by its title and body until a stable taxonomy is justified. These are genuine asset attributes rather than duplicated relationships. ObjectTypes gain a dedicated `datetime` PropertyKind whose value must be RFC 3339 with `Z` or an explicit UTC offset, such as `2026-09-23T14:30:00+08:00`; timezone-free local timestamps are invalid. Chronological operations compare the parsed instant, while storage preserves the authored offset so the source's local-time context is not silently rewritten. Relationships use explicit Markdown links rather than a `projects` property or mirrored relation lists. Markdown remains authoritative, while a rebuildable `links(source_id, target_id)` index derives Page-to-Page edges for reverse relationships and timeline queries; it stores no copied titles, paths, timestamps, or relation semantics. The time field key and name do not vary by ObjectType, while type-specific properties remain separate.

The default Meeting ObjectType has only `occurredAt` as a structured property. Participants, Projects, Decisions, and other related assets are represented by Knowledge links; Meeting does not mirror them in `attendees`, `projects`, or other relation properties. Its subject, agenda, notes, and outcomes stay in the title and Markdown body.

The default Project ObjectType has a `status` property using the shared lifecycle groups, with `Not started`, `In progress`, and `Done` as its initial labels. It has no `due` property: deadlines belong to a future action-system model rather than the first Knowledge asset layer. Creating a Project does not create a Milestone or a placeholder Event. When later raw material or authored content provides evidence for a milestone, Knowledge organization may create a time-bearing Event and link it to the Project; milestone creation is evidence-driven rather than an initialization side effect. A Project's history remains the dynamic timeline of linked time-bearing assets.

The default Person ObjectType has `email` (`email`) and `phone` (`phone`) properties. It does not keep `company` as free text because organization names would become duplicated, unresolvable pseudo-relations. The first version includes an Organization ObjectType for companies, teams, customers, suppliers, and other stable organizations; Person membership and all other relationships to it use Knowledge links.

The default Organization ObjectType has only an optional `website` (`url`) property. Potentially multi-valued contact details and still-unproven classifications remain in the body rather than being forced into lossy scalar fields; they can become properties later when query requirements justify their semantics.

The default Note ObjectType retains `tags` (`multi-select`) for lightweight classification when material has no stronger ObjectType. Tags do not encode Page relationships and may not replace Knowledge links to Persons, Projects, Meetings, Decisions, Events, or other assets.

The first PropertyKind set is `text`, `number`, `checkbox`, `date`, `datetime`, `url`, `email`, `phone`, `select`, `multi-select`, and `status`. A `status` property's options are labeled for the domain but each belongs to exactly one lifecycle group: `not_started`, `in_progress`, or `complete`. This keeps lifecycle queries stable without forcing every ObjectType to expose the same labels. Page title, creation time, and update time remain built-in Page metadata rather than configurable properties. Page relationships use Knowledge links, so the previous `relation` PropertyKind is removed. People, files, formula, and rollup properties are deferred until Folio has the corresponding identity, attachment, or computation semantics instead of imitating their names without their behavior.

Options for `select`, `multi-select`, and `status` have stable IDs distinct from their mutable display names. Page frontmatter stores the option ID, or an array of IDs for `multi-select`; renaming an option therefore does not require rewriting every Page or invalidate historical values. Each option may also carry a presentation-only `color` selected from Folio's fixed palette; arbitrary CSS values are not part of the model. A status option additionally stores its lifecycle group. Free-form string arrays are not used as option identity, and color never participates in value equality.

An option referenced by any Page cannot be deleted. The user may rename it, recolor it, or change the affected Page values first; Folio does not silently clear values or leave an option ID that the active ObjectType can no longer interpret.

A PropertyDefinition with a non-empty value on any Page likewise cannot be deleted. The values must be migrated or cleared first; unused properties may be removed. Folio does not silently erase typed frontmatter or preserve newly orphaned property values as hidden metadata.

The first version does not support changing an existing property's `kind`, even when its current values happen to validate as another type. A type change requires creating a new property, explicitly migrating values, and then removing the unused old property; Folio provides no implicit conversion path.

The first version exposes no UI entry point for changing an existing property's stable `key` or `kind`. Further schema-migration and property-editor behavior is deliberately deferred rather than expanding the Knowledge intake delivery into a general ObjectType migration system.

Folio internal links use the stable Markdown target `folio-page:<pageId>`; the visible label is presentation only. The index accepts only this identity form for Page relationships, reports missing target IDs as broken links, and makes no promise that external Markdown software can navigate Folio's custom scheme.

The Knowledge asset layer represents every Page-to-Page relationship with these links, including Meeting participants and Project associations. Default ObjectTypes do not mirror the same edges in `attendees`, `projects`, or similar relation properties; ordinary URLs and raw-source citations are not Page graph edges and therefore do not enter `links`.

Wiki indexing is change-driven rather than read-driven. During Vault initialization and after one in-app canonical Wiki change, Folio parses the resulting Markdown state and refreshes `wiki_pages`, `wiki_object_types`, and the derived `links(source_id, target_id)` index once in a single database transaction. Ordinary snapshots, Page reads, reverse-link queries, and timeline queries read that projection without rescanning the filesystem. No per-link dirty flags, cursors, or incremental synchronization ledger are introduced. Startup reconciliation for Wiki changes made externally while Folio was not running is deferred; the first version does not add an unconditional startup scan or indexed-commit state for that case.
